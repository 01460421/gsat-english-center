**五個重點**

1. **每個階段結束都是可以對外使用的網站**。下一階段沒做完，上一階段的功能照樣可用；延期只會讓新功能晚到，不會讓網站壞掉。

5. **公開宣傳要等兩件事**：網站已換到自訂網域，以及律師看過隱私權政策、服務條款與未成年同意機制（§11 D6）。建議在 Phase 3 結束（12/3）時兩件都完成。

## 1. 規劃前提

### 1.1 人力與單位

- 開發：一位開發者帶 Claude Code 代理；代理同時負責離線內容（出題、驗證、解析、單字增補）。代理的運算不算在人日裡，但「開批次規格、跑代理、看退件、修工具」算。
- 審核：站主一人（SPEC §5.8 的抽樣規則與每組分鐘數）。
- 估計是**計畫值，不是承諾**；每個階段結束時依實際耗時重估下一階段。

### 1.2 完成的定義

- 每個階段的「驗收標準」就是完成的定義；全部通過才算做完。驗收不過的項目留在原階段，不帶著缺陷往下走。
- 驗收標準分兩類：**必要**（安全、隱私、計費、計分正確性、受保護內容不外流）與**體驗**（介面加分項）。時間不夠時只能延後體驗類，必要類不延後。
- 日期以週四為界（今天 2026-10-08 是週四）。

### 1.3 每次上線的固定步驟

1. PR 通過 CI（型別、單元測試、Playwright、`validate_exam.py`、無損匯入測試、受保護內容掃描、只增不減守門）。
2. 匯入或遷移前在 D1 Time Travel 記書籤（ARCHITECTURE §9.5）。
3. 先部署 Worker、再部署前端；跑冒煙測試（首頁、一份歷屆卷、一次單字查詢；有登入後加登入與交卷）。
4. 後台健康檢查全綠（Phase 2 起）；有 AI 後加「啟動檢查」全綠（ARCHITECTURE §6.3）。
5. 更新站內「更新紀錄」；涉及隱私權政策或條款的改版，版本號遞增，使用者下次登入重新同意。

### 1.4 資料庫遷移的節奏

`0001_init.sql` 一次建好全部 56 張表（DB_SCHEMA §2.1）；各階段只是開始寫入不同的表。之後的結構調整一律新增 `0002_*.sql` 起的遷移，只加不改；**凍結期不跑結構遷移**（緊急修正除外）。
